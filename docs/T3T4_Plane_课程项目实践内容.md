**软件体系结构课程项目实践 T3-T4**

**T3 架构设计**

基于 T2 阶段对 MiniPlane（轻量级团队项目协作与缺陷跟踪系统）的需求用例分析与质量属性场景，本部分综合运用软件体系结构风格和模式、质量属性设计策略，给出系统的核心架构设计决策。

**1\. 整体架构风格选择**

为了满足系统高内聚、低耦合、易于维护与扩展的核心要求，结合 GitHub 开源项目 Plane 的技术演进，本系统（MiniPlane）采用前后端完全分离的分层体系结构风格。

前端表现层： 采用 Next.js (React 框架) 构建单页面应用。

后端业务层： 采用 Django (Python) 构建 RESTful API。

调度与存储层： 采用 PostgreSQL 作为主数据库，引入 Redis 作为核心事件派遣器（Dispatcher）的底层支撑，并引入 MinIO 解决附件存储的无状态化问题。

- MiniPlane 中，为了应对高并发和系统解耦，系统核心大量运用了有独立事件派遣模块的事件系统。具体落地为以下三个核心业务场景：

- **前端多视图联动：有独立调度模块的前端事件总线**
- 对应需求： F8（看板视图）、F9（列表视图）的数据实时同步。
- 技术映射： Next.js 全局状态管理（如 Zustand/Redux 或 React Context）。
- 术语与机制对齐：
- 在前端，我们摒弃了组件间混乱的互相调用或深层传递，而是将全局 State 作为一个独立的 Dispatcher。当用户在看板中拖动任务更改状态时，看板组件触发隐式调Dispatcher 接收到状态变更事件后，通过选择广播式，仅将变更数据推送到注册过监听的列表视图或统计视图组件，触发局部重渲染。这极大地提升了前端的可修改性。
- **后端耗时任务流转：点对点模式**
- 对应需求： F15（操作日志记录）、批量数据处理等。
- 技术映射： Django + Celery Worker (后台任务队列) + Redis。
- 真实 Plane 源码中包含 plane-worker 容器。我们将 Redis 作为消息队列。当需要记录复杂操作日志时，Django 接口（Producer）将任务打包成事件丢入 Redis 队列。后端的 Worker 作为唯一消费者连接到队列。根据点对点模式的特性，事件被取出执行后即从队列中删除。这保证了核心 API 的极速响应，同时确保任务不被重复执行。

**实时协作与通知：发布-订阅模式 (Publish-Subscribe)**

- 对应需求： F14（相关成员实时收到系统通知）。
- 技术映射： WebSocket 长连接 / Django Signals。
- 系统设立通知主题，例如 Project*Updates*{ID}。当前在线并进入该项目工作空间的团队成员，其前端 Next.js 客户端会自动作为订阅者（Subscriber）向该 Topic 注册。当某成员评论了任务，后端 Dispatcher 将事件广播给该 Topic 下的多个订阅者，实现多端的通知铃铛同时亮起。

针对 T2 中提取的关键非功能性需求，系统在架构级别采用以下具体的设计策略：

| ------------------------ | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **质量属性**             | **应对场景举例**                                    | **架构级设计策略 (Design Tactics)**                                                                                                                     |
| 性能 (Performance)       | QS1: 10万条数据多条件查询，95%请求响应时间 ≤ 2 秒。 | 引入并发与缓存策略：对于高频访问且不常变动的项目任务列表引入 Redis 进行缓存；数据库中针对高频查询字段建立复合索引；前端采用分页机制限制单次返回数据量。 |
| 可用性 (Availability)    | QS2: 后端实例故障，1 分钟内恢复，月可用率 ≥ 99.5%。 | 心跳检测与主动冗余：后端服务采用“无状态(Stateless)”设计，通过 Nginx 进行反向代理与负载均衡。配置心跳探活机制，节点宕机自动剔除并平滑重定向流量。        |
| 安全性 (Security)        | QS3: 未授权或越权用户拒绝率 100%。                  | 统一拦截与 RBAC 访问控制：采用基于 Token（如 JWT）的无状态身份认证机制。在后端网关前置统一的拦截器，严格执行基于角色（RBAC）的访问控制，防止水平越权。  |
| 可修改性 (Modifiability) | QS4: 新增“日历视图”，开发工作量 ≤ 3 人日。          | 局部化修改与接口复用：表现层采用组件化设计，后端坚持“面向接口编程”。新增视图时，直接复用现有“任务查询接口”，仅在前端新增视图组件，不影响核心模块。      |
| 数据可靠性 (Reliability) | QS7: 异常退出时，已提交的数据不丢失。               | 事务机制与持久化：在业务逻辑层强制启用数据库声明式事务管理，确保“任务状态更新”与“操作日志记录”等联动操作满足原子性（ACID）。                            |

**3\. 评估结论与架构优化建议**

针对评估中暴露出的可用性风险点（AD4），提出以下优化建议：

服务无状态化改造：将本地文件存储修改为独立的分布式对象存储（如 MinIO 或 OSS），使后端服务完全回归“无状态”属性。

1.  引入负载均衡高可用：后端业务服务至少部署 2 个实例，通过 Nginx 负载均衡实现故障自动切流，彻底消除单点故障。
